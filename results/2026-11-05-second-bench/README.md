# 2026-11-05 2차 벤치: 프로세스 분리 하네스, W × RTT 매트릭스 + 리더 크래시 복구

1차(`results/2026-11-04-first-trend`)의 한계 — 4 노드가 한 프로세스를 공유해 RTT 0 에서 CPU 경합으로 결과가 무효 —
를 없애기 위해 **노드 하나 = OS 프로세스 하나**, 실제 TCP, 노드별 `GOMAXPROCS=2` 로 다시 측정한 1회 실행이다.
수치는 반복 측정 전 값이며, 아래 "이상 징후" 절의 셀은 TPS 를 그대로 믿으면 안 된다.

## 환경

- 머신: Apple M1 Pro (MacBookPro18,1, 10 CPU), 16 GB, macOS 15.7.3 (Darwin 24.6.0); Go go1.27.3 darwin/arm64
- 포크: `SmartBFT` main @ 18fad70c (`bench/go.mod` 의 `replace` 로 참조)
- 하네스: `bench/cmd/node` + `bench/cmd/matrix` (`bench/README.md` "2차 하네스" 절). N=4, 노드마다 프로세스 1개,
  `GOMAXPROCS=2` (4 × 2 = 8 ≤ 10 코어), 127.0.0.1 TCP, 링크별 FIFO + 송신 측 편도 지연 RTT/2, 인메모리 WAL
- 부하: closed-loop K=1024 (처리량 셀은 리더 프로세스 안에서 로컬 제출), 요청 64 B,
  `RequestBatchMaxCount=50`, `RequestBatchMaxInterval=50ms`
- 설정: `lib.Config` (1차와 동일) — `LeaderRotation=false`, `DecisionsPerLeader=0`, `PipelineDepthMax=W`,
  `RequestPoolSize=20000`, `IncomingMessageBufferSize=1000`, `RequestForwardTimeout=30s`, `RequestComplainTimeout=60s`,
  `RequestAutoRemoveTimeout=120s`, `LeaderHeartbeatTimeout=60s`/`Count=10` (→ 리더의 미결 pre-prepare 재전송 주기 6 s),
  `ViewChangeTimeout=60s`, `NumOfTicksBehindBeforeSyncing=10`, `CollectTimeout=1s`
- 측정: 모든 노드가 결정 30회를 전달하면(READY) 각자 15 s 측정. 표의 값은 리더(노드 1)의 Deliver 기준.
  `view_changes/syncs/warnings/dropped` 는 4 노드 합
- 크래시 셀: 위 설정에 `-vc-timers` (`RequestForwardTimeout=500ms`, `RequestComplainTimeout=2s`,
  `LeaderHeartbeatTimeout=5s`/`Count=10`, `ViewChangeTimeout=20s`, `ViewChangeResendInterval=5s`), RTT 50 ms, W=4 와 W=1.
  클라이언트(K=1024)는 노드 4 프로세스에서 돌며 워커별로 노드 1,2,3,4 에 라운드로빈 제출, 3 s 안에 전달되지 않으면
  다음 노드에 재제출. 모든 노드 READY 5 s 뒤 노드 1 에 SIGKILL(T0); 살아남은 노드의 측정 창은 40 s

## 읽기

### TPS
- **RTT ≥ 50 의 깨끗한 셀(※ 없음)은 1차와 같은 값을 재현한다**: W=1 603/313/160 (1차 613/317/—), W=4 @100 1,240
  (1차 1,253), W=8 @50 4,586 (1차 K=256 3,077 → K=1024 로 부하 상한이 풀림), W=8 @100 1,266 vs 1차 K=1024 2,506 (이번엔
  15 회 sync·4 s 정지가 섞임). 즉 **이탈이 없으면 TPS ≈ W × (W=1 TPS)** 가 RTT 50–200 에서 유지된다 (W=8 @50: 7.6×, @200: 7.7×).
- ※ 셀은 이탈·정지 시간이 섞인 값이라 추세선에 쓰면 안 된다. 특히 W=2 열(50/100/200 모두 ※, 5.3/3/5.4 s 정지)은
  W=1 과 거의 같거나 낮게 나왔는데, 이는 깊이 2 의 창이 가장 좁아(한 결정만 뒤처져도 이탈) 이탈이 가장 잦기 때문이다.
- **RTT 0**: W=1 131,818 TPS (2,636 결정/s) 는 15 s 내내 균일하고(초당 12.4–13.7만), 1차의 182k 와의 차이는 protobuf
  직렬화·TCP·GOMAXPROCS=2 비용이다. W>1 은 위 (b) 영구 정지로 "첫 1 s 의 버스트 ÷ 15 s" 가 되어 무의미하다. 정지 전 버스트
  구간의 속도(W=2 164k/s, W=4 107k/s, W=8 74k/s)는 W=1 보다 높지 않다 — RTT 0 은 CPU 바운드라 파이프라인이 도움이 안 된다.

### p99 vs W (RTT 별)
- **RTT 50**: 1,746 (W1) → 6,611 (W2 ※, 5 s 정지) → 2,346 (W4 ※, 1.9 s 정지) → **289 (W8, 깨끗)**. 깨끗한 두 점만 보면 p99 는
  W 에 반비례해 떨어진다(closed-loop: 지연 ≈ K/TPS). ※ 셀의 p99 는 정지 길이 그 자체다(재전송 6 s 상한).
- **RTT 100**: 3,345 → 5,049 (W2 ※) → **965 (W4, 깨끗)** → 4,536 (W8 ※, 4 s 정지). 깨끗한 점: W1→W4 에서 3.5× 감소.
- **RTT 200**: 6,479 → 8,832 (W2 ※) → **1,889 (W4, 깨끗)** → 1,030 (W8, sync 1 회, 정지 없음). 깨끗한 점은 W1→W4→W8 에서
  6,479→1,889→1,030 으로 단조 감소하며 W4→W8 에서 기울기가 꺾인다 (TPS 가 620→1,230 으로 2× 늘었는데 p99 는 1.8× 만 줄어
  꼬리가 두꺼워지기 시작; p99/p50 비가 W4 1.22 → W8 1.11 로 오히려 좋아지므로 "굽음" 은 아직 작다).
- **RTT 0**: 16 → 12 → 8.3 → 8.7 ms — 정지 전 1 s 버스트의 값이므로 W>1 은 참고만.
- 요약: **p99 는 W 와 함께 오르지 않는다** — 팔로워가 창 안에 머무르는 동안은 W 에 반비례해 내려가고, 꺾이는 지점은 이번
  범위(W≤8, K=1024)에서는 보이지 않는다. 대신 p99 를 지배하는 것은 W 가 아니라 **이탈 → 정지(최대 6 s)** 의 유무이며,
  이탈 확률은 창이 좁은 W=2 에서 가장 높고 W=8 에서 가장 낮았다(※ 셀 수: W2 3/4, W4 1/4, W8 2/4 — 단 W8 은 정지가 더 길다).

## 주요 발견: W>1 에서 뒤처진 팔로워의 "이탈" 과 리더 정지 (하네스 아닌 포크의 동작)

프로세스를 분리하자 1차에서 보이지 않던 라이브러리 동작이 드러났다. 매트릭스 전에 격리 실험(W=4, RTT 50, 10 s,
`-verbose`) 으로 확인한 메커니즘은 다음과 같다 (`internal/bft/view.go` 의 순번 라우팅 주석과 일치).

1. 뷰는 `[low, low+W]` 범위의 순번만 받는다. 리더가 결정 N 을 전달하고 즉시 N+W 를 제안하므로, 그 pre-prepare 가
   도착하는 시점에 **두 결정 이상 뒤처진 팔로워**(low ≤ N−1)는 `"got message from 1 with sequence N+W but our
   sequence is N-1"` (Info) 를 남기며 pre-prepare 를 **조용히 버린다**. 재요청은 없다.
2. 그 팔로워는 빈 슬롯 뒤의 순번을 처리할 수 없어(prefix 규칙) 멈춰 있다가, 정족수(리더+다른 팔로워 2)가 W 결정을
   더 진행해 창 밖의 커밋 투표 2개를 보면 `"Seen 2 votes for digest ... but I am in view 0 and seq N-1"` (Warn) →
   `Sync()` 로 따라잡는다 (이 하네스에서는 피어에서 결정을 받아 Deliver).
3. Sync 뒤 뷰를 새 순번에서 다시 시작하지만, 그 사이 리더가 보낸 in-flight pre-prepare 들은 이미 지나갔다. 지속 부하
   아래에서는 정족수가 한 웨이브(W 결정, RTT 50 에서 ≈85 ms)마다 전진하므로 팔로워는 매 웨이브 "Seen 2 votes → Sync"
   를 반복한다 (격리 실험: 노드 3 이 10 s 동안 29회 sync, 200–300 ms 간격). 되돌아오는 길은 리더의 미결 pre-prepare
   재전송(`LeaderHeartbeatTimeout/Count` = 6 s)이나 리더가 쉬는 순간뿐이다.
4. 팔로워 둘이 동시에 이탈하면 리더(커밋 3개 필요)는 정족수를 잃고 정지한다. 재전송은 **pre-prepare 만** 다시 보내므로,
   창 밖에 있을 때 그 순번의 prepare/commit 투표까지 놓친 팔로워는 재전송을 받아도 prepared 상태에 못 가 commit 을 내지
   못한다. 따라서 (a) 투표는 받았고 pre-prepare 만 놓친 경우 → 6 s 재전송에서 복구(히스토그램이 `[.., 130900, 0×6, 550, ..]`
   처럼 6 s 주기 버스트; 예비 실행에서 관찰), (b) 투표도 놓친 팔로워가 둘이면 → **뷰 체인지(여기서는 60 s+ 타이머)까지
   영구 정지**. 이번 실행의 RTT 0 W=2/4/8 셀이 (b) 다: 창 시작 ≈1 s 뒤부터 끝까지 전달 0 (w4-rtt0: 21:54:06.96 에 노드 3 은
   순번 2134, 노드 4 는 327 에 있을 때 2139–2142 웨이브가 지나갔고, 12.5 s 의 재전송 뒤에도 둘 다 commit 을 못 냄).
   `-vc-timers`(재전송 0.5 s) 에서는 (a) 의 정지가 0.5 s 로 줄지만 이탈 루프 자체는 그대로다.
5. 이탈의 방아쇠는 팔로워가 한 웨이브 안에(RTT 0 에서는 ≈1.5 ms, RTT 50 에서는 ≈25 ms) 두 결정 뒤처지는 지터다.
   `GOMAXPROCS=2` 프로세스에서 확률적으로 일어나며(같은 설정의 10 s 실행이 2,173 TPS 로 깨끗하기도, 550 TPS 로 3 s
   정지하기도 했다), 1차의 단일 프로세스(GOMAXPROCS=10, 인메모리 전달)에서는 지터가 작아 RTT ≥ 50 에서 전혀 나타나지
   않았다. W=1 에서는 창이 `[low-1, low+1]` 이고 리더가 한 결정씩만 전진하므로 "Seen 2 votes → Sync" 뒤 바로 복귀한다.

따라서 W>1 셀의 TPS 는 "파이프라인 효율 × (이탈·정지가 없었던 시간 비율)" 이다. 아래 표에서 `syncs>0` 인 셀(※)은
팔로워 이탈이 있었던 셀이고, 리더 히스토그램의 0 인 초가 있는 셀은 정지가 있었던 셀이다. 라이브러리 쪽 후속 과제:
창 밖 pre-prepare 를 버리지 말고 보관하거나 즉시 재요청(또는 Sync 직후 in-flight pre-prepare 재전송 요청)하는 것.

## 이상 징후 (숨기지 않음)

- 뷰 체인지: 처리량 16 셀 모두 0. 설정 거부·제출 실패·링크 큐 드롭: 0. `clock_jump_ms` ≤ 0.4 (잠자기 없음).
- `syncs`/`warnings` 는 전부 팔로워의 `Seen 2 votes for digest ... but I am in view 0 and seq N` → `Sync()` 이며 1:1 로 대응한다
  (warnings == syncs). 리더는 어떤 셀에서도 경고·sync 가 없다.
- "리더 전달 공백" 열: 측정 창 안에서 리더의 전달이 1 s 이상 끊긴 횟수와 전달 0 인 초의 수. RTT 0 W>1 은 창 끝까지
  정지해 "뒤에 전달이 없는" 공백이라 0 으로 집계된다 — 리더 히스토그램(측정 창): w2-rtt0 `[164350, 77000]`,
  w4-rtt0 `[106900]`, w8-rtt0 `[74100]` 뒤 전부 0.
- `follower_lag`(종료 시 리더 − 가장 느린 팔로워 결정 수)는 최대 6 — 1차의 10,696/52,110 같은 영구 지연은 없다 (하네스 Sync 가
  피어 상태 전송으로 따라잡음).

## 리더 크래시 복구

클라이언트는 노드 4 에 K=256 (워커별 라운드로빈 1,2,3,4; 3 s 미전달 시 다음 노드로 재제출). T0 = 노드 1 SIGKILL.
"파이프라인 꼬리" 가 `-` 인 것은 생존자 셋이 T0 뒤 34 ms 까지 이미 받은 pre-prepare 를 계속 전달했기 때문(공백이 T0 뒤에
시작)이다. 공백은 (T0+34 ms, T0+2,683 ms) 하나.

### 읽기

- **W=4: 뷰 체인지 정확히 1회, 복구 2.68 s.** 생존자 셋(2,3,4)은 T0 뒤 34 ms 까지 이미 받은 pre-prepare(순번 126 까지)를
  스스로 커밋한 뒤, 전달(forward)된 요청의 불만 타이머(0.5+2 s)로 T0+2.1 s 에 뷰 1 을 시작하고(리더 노드 2) T0+2.68 s 에 첫
  전달(순번 127). 꼬리 전달이 in-flight 를 모두 비웠으므로 "In-flight view ... has committed a decision" 은 0 회였다
  (폐기한 1차 실행에서는 in-flight 4개가 2 s 간격으로 재커밋돼 뷰 1 시작까지 7 s 걸렸다). 복구 뒤 15 s TPS 596 (크래시 전
  716, K=256). 복구 뒤에는 노드가 3개뿐이어서 정족수 여유가 0 이고, 위 "이탈" 메커니즘으로 팔로워 하나가 빠지면 리더가
  곧장 멈추므로 복구 뒤 TPS 는 크래시 전보다 낮고, 격리 실행에서는 복구 6–10 s 뒤 추가 뷰 체인지(뷰 2)도 관찰됐다
  (이번 실행은 정확히 1회).
- **W=1: 뷰 체인지 5회, 첫 전달까지 30.5 s.** 뷰 1·2·3 이 T0+2.0/4.7/7.3 s 에 2.6 s 간격으로 이어지고 그 어느 뷰에서도
  전달이 없다가, `ViewChangeTimeout` 20 s 뒤 T0+30.5 s 에 뷰 5 가 시작되어서야 첫 전달(그 뒤 창이 끝나 15 s TPS 는 17 로
  불완전). 원인은 다음 경주이며 포크/원본 공통 경로(깊이 1)의 라이브니스 문제다. `-debug` 로 확보한 전체 로그(격리 실행):
  새 리더(노드 2)는 뷰 1 시작(21:51:41.853) 직후 순번 76 을 제안해 NewView·PrePrepare·Prepare 를 0.3 ms 안에 연속
  송신한다. 팔로워(노드 3)는 셋을 한 묶음으로 받고(41.8804) NewView 처리 → 뷰 0 중단 → **뷰 1 시작(41.8807)** 순으로
  진행하므로, 그 사이 도착한 PrePrepare 는 아직 뷰 0 인 뷰 인스턴스로 라우팅돼 버려진다. 깊이 1 에서는 리더가 미결
  pre-prepare 를 재전송하지 않으므로(`resendTick` 은 W>1 리더에만 있음) 제안 76 은 영원히 멈추고, 팔로워들은 2.5 s
  (`RequestForwardTimeout`+`RequestComplainTimeout`) 뒤 불만 → 뷰 2 → 같은 경주 반복 → 뷰 3 … 으로 이어진다
  (노드 3 의 "Processed proposal with seq 76" 은 자신이 뷰 2 리더가 되어 제안한 것 하나뿐). 1차 하네스(인메모리)에서도
  링크당 FIFO 이므로 같은 경주가 가능하지만 측정하지 않았다. **W=4 가 복구되는 것은 포크가 W>1 에 추가한 pre-prepare
  재전송(`LeaderHeartbeatTimeout/Count`, 크래시 셀에서는 500 ms) 덕분이다.** 라이브러리 후속 과제: 새 뷰 시작 전에
  도착한 상위 뷰 메시지를 버퍼링하거나, 깊이와 무관하게 첫 pre-prepare 를 재전송할 것.
- 하네스 쪽에서 고친 것: (1) 뷰 체인지 중 `Sync()` 가 호출될 때 `Transport.Fetch` 가 죽은 피어의 응답을 3 s 기다려
  새 리더를 세웠던 문제 → 연결된 피어만 기다림; (2) 클라이언트를 다음 리더(노드 2)가 아닌 노드 4 에 둠; (3) K=256.

## 1차 벤치와의 차이

| | 1차 (2026-11-04) | 2차 (이 실행) |
|---|---|---|
| 배치 | 1 프로세스, 4 인스턴스, GOMAXPROCS=10 | 4 프로세스, 각 GOMAXPROCS=2, TCP |
| 네트워크 | 인메모리 채널, 링크별 goroutine | TCP, 링크별 FIFO 큐, 송신 측 지연 |
| 직렬화 | 없음 (포인터 전달) | protobuf 마샬/언마샬 (링크 goroutine) |
| Sync | 공유 레저에서 즉시 catch-up | 피어 상태 전송 (같은 TCP 연결) |
| K | 256 (보조 1024) | 1024 (크래시 셀 256) |
| RTT | 0, 50, 100 | 0, 50, 100, 200 |
| 크래시 셀 | 없음 | W=4, W=1 @RTT 50 |

- **RTT 0 은 유효해졌는가?** 부분적으로. 리더는 더 이상 CPU 경합으로 막히지 않아 W=1 에서 2,600 결정/s·130k TPS 를 15 s 내내
  유지하고 `view_changes=0`, 종료 시 팔로워 지연도 수 결정 이내다. 그러나 `syncs==0` 은 아니다: 결정 주기가 0.4 ms 라
  팔로워의 1–2 ms 지터만으로 두 결정이 뒤처져 "Seen 2 votes → Sync" 가 반복된다(W=1: 15 s 동안 수백–천여 회, 각 sync 는
  수 ms 안에 피어에서 따라잡음). W>1 RTT 0 셀은 위 "이탈" 메커니즘 때문에 6 s 정지가 섞여 TPS 가 W 에 따라 **감소**한다 —
  1차와 같은 방향의 추세지만 원인은 CPU 경합이 아니라 창 밖 pre-prepare 폐기다.
- **RTT ≥ 50 의 W 추세는 1차와 일치하나 더 거칠다.** 1차는 전 셀 sync 0 으로 W 에 거의 선형이었다. 2차는 깨끗한 셀에서는
  같은 값(W=1: 593 vs 613 @50, 313 vs 317 @100; W=8 @100: 2,453 vs 2,506(K=1024))을 재현하지만, 이탈이 난 셀은
  크게 낮다. 즉 **파이프라인의 이득은 "팔로워가 한 웨이브 안에 머무를 때" 만 실현된다.**
- 1차에서 "정상 동작" 으로 분류한 `Got pre-prepare for sequence N but we're in sequence M` 경고는 2차에서 보이지 않고
  대신 `Seen 2 votes ...` 와 `got message ... but our sequence is` 가 나타난다: 1차에는 재전송이 이미 전달한 팔로워에게
  닿았고, 2차에는 재전송이 **아직 못 받은** 팔로워를 구한다.

## 실행 중 사고 (1차 실행분, 폐기)

첫 전체 실행(21:01–21:41) 중 머신이 유휴 잠자기에 들어가 w1-rtt0 와 w1-rtt50 의 측정 창이 벽시계로 17/16 분이 되었고

기록하고 2 s 이상이면 note 에 적는다.
